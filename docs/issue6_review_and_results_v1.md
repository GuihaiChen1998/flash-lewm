# Issue #6 评审与验证结果 v1（2026-11-13）

对象：issue #6「Flash-LeWM：共享动作前缀与异步分支搜索」。
环境：Linux#1，单张 RTX A6000，conda `sglang`（torch 2.6.0 / transformers 4.54.1），官方 Fast-LeWM Push-T checkpoint，
LeWM 原始 `pusht_expert_train.h5`。只做了 Push-T。

## 1. 结论

| 假设 | 判定 | 依据 |
|---|---|---|
| H1 精确复用 | 精确性成立，加速在官方配置下不成立 | 代价相对误差 ≤ 3e-6，top-k 100% 一致；但 N=300 时缓存路径比稠密慢约 45–52%，N ≥ 3000 才快 26–51% |
| H2 分支搜索 | 不成立 | 同为约 9000 次评估，闭环成功率比官方 CEM 低 4.6–5.1 个百分点（n=1010，95% CI 不含 0） |
| H3 异步推进 | 单 GPU 上不成立 | 每次前向有约 4.5 ms 固定开销，N ≤ 300 时与批大小无关；逐分支调用使单次规划从约 0.16–0.19 s 变成 2.2–2.6 s |

真正的瓶颈不在 issue 假设的地方。官方路径单次规划 487 ms，其中 63% 是每轮 CEM 都重新编码一次观测图和目标图
（30 轮 × 2 次 ViT，结果每轮都相同）。动作前缀编码器只占 10%，issue 里「省 19% token 位置」最多对应官方耗时的 2%。

据此改成的方案 **FlashCEM**：潜向量只编码一次 + 把整轮 CEM（采样→评分→top-k→重拟合）编译成一张静态图。
更新规则与官方 CEMSolver 相同。闭环结果（n=1010 回合，配对 bootstrap）：

| 方法 | 成功率 | 单次规划延迟 | 相对官方的成功率差 [95% CI] | 加速 |
|---|---:|---:|---:|---:|
| 官方求解器（每轮重编码）300×30 | 89.0% | 467 ms | — | 1× |
| 只缓存潜向量 300×30 | 89.2% | 165 ms | +0.2 [−0.6, +1.0] | 2.8× |
| **FlashCEM 300×30** | 88.9% | 64.8 ms | −0.1 [−1.6, +1.4] | 7.2× |
| FlashCEM 300×15 | 87.5% | 35.1 ms | −1.5 [−3.1, +0.1] | 13.3× |
| FlashCEM 300×10 | 87.7% | 25.2 ms | −1.3 [−2.9, +0.3] | 18.6× |
| 宽批 1000×10，精英 30（未编译） | 90.2% | 68.8 ms | +1.2 [−0.3, +2.8] | 6.8× |
| issue 算法：树 L15 s1 m20 均分，同步 | 83.9% | 132 ms | −5.1 [−7.4, −3.0] | 3.5× |
| issue 算法：树 自适应预算，同步 | 84.5% | 158 ms | −4.6 [−6.8, −2.4] | 2.9× |
| issue 算法：树 自适应，3000 次评估 | 82.0% | 59 ms | −7.0 [−9.4, −4.8] | 7.9× |
| issue 算法：树 自适应，异步（n=50） | 86.0% | 2633 ms | −6.0 [−14.0, +2.0] | 0.18× |
| 改进：分支同时重拟合前缀（n=250） | 90.0% | 162 ms | −0.4 [−4.4, +3.6] | 3.0× |

延迟含图像编码（约 5–7 ms），P95 与均值相差不到 3%。FlashCEM 300×30 与官方等质量；
减到 10–15 轮再快一倍，但成功率区间下界到 −3 个百分点，是否可接受要看用途。

## 2. 各实验

### E0 官方路径剖析（8 个配对，`results/e0_profile.json`）

| 部分 | 耗时 | 占比 |
|---|---:|---:|
| 图像编码（ViT + projector，每轮 2 次，共 60 次） | 301 ms | 63% |
| 终点预测器 | 89 ms | 19% |
| 动作前缀编码器 | 49 ms | 10% |
| 其余（H2D 拷贝、采样、top-k） | 36 ms | 8% |

来源：`JEPA.get_cost` 每次调用都执行 `self.encode(goal)`，`rollout` 里再 `self.encode(_init)`。
把两个潜向量提到循环外后单次规划 154 ms（3.2×），同一批候选上的代价相对误差 ≤ 3.5e-4、top-30 完全一致。

### E1 前缀 K/V 缓存（`results/e1_prefix_cache.json`）

`PrefixScorer` 实现 Prefill / Append，`s=0` 表示只共享潜状态 token（对同一观测的所有候选、所有 CEM 轮都成立）。
精确性：14 种树形状 × 4 个配对，代价最大相对误差 3.1e-6，top-k 重合 100%，Spearman ≥ 0.9999999。

| 叶子数 N | 形状 (L×K, s) | 稠密 | 缓存（含 prefill） | 变化 |
|---:|---|---:|---:|---:|
| 300 | 1×300, s=0 | 4.65 ms | 6.72 ms | +45% |
| 300 | 15×20, s=1（issue 示例） | 4.67 ms | 7.04 ms | +51% |
| 300 | 15×20, s=3 | 4.65 ms | 7.06 ms | +52% |
| 3000 | 1×3000, s=0 | 16.5 ms | 12.3 ms | −26% |
| 3000 | 15×200, s=1 | 16.6 ms | 11.7 ms | −30% |
| 3000 | 15×200, s=3 | 16.6 ms | 9.8 ms | −41% |
| 30000 | 15×2000, s=3 | 160 ms | 78 ms | −51% |

延迟随批大小（稠密，单观测）：N=10/30/100/300 分别是 4.51/4.56/4.60/4.70 ms，N=1000 是 6.4 ms，
N=3000 是 17.3 ms，N=10000 是 54.7 ms。N ≤ 300 时完全由固定开销决定，这就是缓存和异步在官方配置下都亏的原因。

指标：返回计划在模型下的代价，与「缓存潜向量的官方 CEM」逐对相除取中位数（越小越好）。

| 方法 | 评估数 | 耗时 | 代价比中位数 |

| 宽批 1000×10 k30 | 10001 | 75 ms | 1.84 |

| 树 自适应，同步，K/V 缓存评分 | 9149 | 648 ms | 1.24 |

（此表计时带逐轮同步和 trace 记录，比闭环里同一方法略慢，只用于方法间相对比较。）
两点值得注意：模型代价主要由迭代轮数决定；但闭环里 10 轮（代价高 3 倍）成功率只低 1–2 个点，
说明把模型代价压到很低对任务成功的边际收益小。

### E5 闭环（`results/e5_closedloop_*.json`，`results/paired_summary_1010.json`）

协议按官方 `eval.py`：数据集起始状态，目标为同回合 +25 步的帧，50 步预算，每 25 步重规划，任一步终止即成功。
回合 = 官方 50 个（seed 42）+ 另抽 960 个（seed 7），共 1010 个。官方求解器在官方 50 回合上是 92%。
环境核对：12 个起点重放专家动作 12/12 成功，渲染帧与数据集帧平均绝对像素差约 0.4/255。

### E7 FlashCEM 离线（`results/e7_flash.json`）

每轮 1.9 ms（未编译 4.6–5 ms）；300×30 单次求解 57 ms，返回计划的模型代价与未编译版相当（比值中位数 0.96）。
首次调用要编译约 7–11 秒，之后复用。不用 CUDA graph 时是 82 ms。

## 3. 对 issue 方案的具体意见

1. **瓶颈判断要先看代码。** issue 第 1 节已注意到「动力学 4.1 s vs 完整 CEM 16.1 s」并把剖析列为 E0，方向是对的；
   但方案主体仍然建立在前缀编码和调度上。剖析结果是前缀编码器只占官方耗时的 10%。
2. **前缀在算法 1 里是冻结的。** 15 个首块从 N(0, I) 采一次就不再动，只有根分支（20% 预算）能改首段。
   闭环里首段正是最先被执行的部分。去掉根分支代价比升到 1.65；让每个分支也重拟合自己的前缀，成功率回到 90.0%（n=250）。
   但那样分支就退化成多个并行的小 CEM，共享前缀也就不存在了。
3. **异步的前提是批大小贵。** 这个模型单次前向在 N ≤ 300 时是固定 4.5 ms。把 300 个候选拆成 15 个分支各自前向，
   是 15 次固定开销。只有在多 GPU / 多流、或单候选代价远大于调用开销的大模型上，异步才可能有净收益。
4. **K/V 缓存只在宽批下划算。** 如果以后走「大 N、少轮」的路线（N ≥ 3000），`s=0` 的潜 token 共享是免费的 26%，可以保留。
5. **评估口径。** 官方 50 回合的标准误约 4 个点，方法间 2–6 个点的差别在 50 回合上看不出来；这次用 1010 回合配对比较。

## 4. 局限

- 只有 Push-T、一个 checkpoint、一张 A6000；Cube / Reacher / Two-Room 没做。
- 运行环境是 torch 2.6 / transformers 4.54，不是官方 requirements 里的 2.10 / 5.3；ViT 用存储的超参重建后严格加载权重。
- 闭环是按官方协议重写的最小循环（`flash_lewm/closedloop.py`），没有走 `World.evaluate_from_dataset`。
- 「异步」是单 GPU 上逐分支独立前向，没有测多 GPU 或 CUDA 多流。
- 树搜索只试了表里这些超参，没有系统调参。
- torch.compile 的 max-autotune 模式在这台机器上长时间不返回，被中止，未纳入结果。

## 5. 下一步建议

1. 把 FlashCEM 接进官方 `eval.py`（替换 `CEMSolver`），在 Cube 上复核。Cube 是 3D 接触操控，结论可能不同。
2. 多环境合批：官方 `batch_size=1` 逐个环境求解，`cem_multi` 已写好但还没测吞吐。
3. 图像编码（5–7 ms）现在占 FlashCEM 300×10 的四分之一，可以同样编译。
4. 如果仍想做分支/异步，建议换到单候选评估贵的设定（更大的世界模型，或多 GPU），先测那里的延迟–批大小曲线再决定。
