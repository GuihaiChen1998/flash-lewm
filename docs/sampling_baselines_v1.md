# 与采样优化类求解器（iCEM、MPPI）的对比与叠加（v1，2026-11-18）

问题：iCEM、MPPI 这类方法也是通过改采样来省时间或提质量。我们的方法要不要和它们比？能不能叠加到它们上面？

## 结论

1. **我们的两个算法部件（承诺前缀 + min 代价）可以直接叠加到 iCEM 和 MPPI 上，而且几乎处处显著提升**：
   4 个环境 × 2 个场景 × 3 种求解器设置共 24 组，21 组显著为正，增益 +4.3 到 +42.7 个百分点；
   唯一不显著的是 Cube 换目标（−1.0 到 +2.7，置信区间跨 0）。
2. **完整方法（FlashCEM + 两个部件）在 8 组里全部高于「iCEM / MPPI 按官方方式部署」**，差值 +5.7 到 +60.0 个百分点。
3. **在相同延迟（1 步）下，完整方法也高于「iCEM + 我们的部件」「MPPI + 我们的部件」**：16 组里 14 组显著，
   只有 Two-Room 静态（+1.3）不显著。原因：10 Hz 下规划耗时一旦低于 100 ms 就只算 1 步延迟，
   iCEM 再省时间也换不来更多；它轮数少（10 轮），质量反而比 30 轮 CEM 差。
4. 所以 iCEM、MPPI 和我们的方法不是互斥的：它们解决「每次规划多快、多准」，我们解决「规划结果怎么在延迟下执行、代价怎么定」。
   50 Hz（每步 20 ms）下也测了（`docs/rate50hz_v1.md`）：只要规划耗时低于一个动作块，再快也没有收益，完整方法仍然最好。

## 求解器实测耗时（Fast-LeWM，RTX A6000，`scripts/e11_solver_latency.py`，机器空闲时）

| 求解器 | Push-T | Two-Room | Cube | Reacher |
|---|---|---|---|---|
| 官方 CEM 300×30（每轮重新编码） | 453 ms | 455 ms | 568 ms | 569 ms |
| CEM 300×30（编码缓存） | 147 | 147 | 187 | 187 |
| iCEM 300×10（编码缓存） | 59 | 60 | 76 | 76 |
| iCEM 100×5（编码缓存） | 35 | 35 | 44 | 44 |
| 官方 MPPI 300×10 | 148 | 149 | 187 | 187 |
| MPPI 300×10（编码缓存） | 55 | 55 | 71 | 71 |
| **FlashCEM 300×30（编译）** | **62** | **62** | **63** | **63** |

官方库的 `ICEMSolver` 在 Fast-LeWM 的打包时域（horizon=1）上会报 IndexError，所以 iCEM 用我们自己的实现
（`flash_lewm/realtime.py`：β=2 的有色噪声、种群按 1.25 衰减、保留 30% 精英、动量 0.1、用上一计划平移热启动、返回最优序列）。
「官方方式部署 iCEM」的耗时按「缓存版耗时 + 官方每轮重新编码的开销」估算：
Push-T / Two-Room 每轮约 10 ms，Cube / Reacher 约 13 ms，得到 iCEM 300×10 约 160–205 ms。

## 配置（10 Hz，延迟步数 = ⌈耗时 / 100 ms⌉）

| 简称 | 求解器 | cfg | 说明 |
|---|---|---|---|
| 官方 CEM 部署 | CEM 300×30 | `sync:5:6:30:last` | 官方做法，延迟 6 步，整段执行 5 块，终点代价 |
| iCEM 部署 | iCEM 300×10 | `sync:5:d:10:last` | d = 2（Push-T、Two-Room）、3（Cube、Reacher），按官方方式部署的估算延迟 |

| iCEM-小 部署 | iCEM 100×5 | `sync:5:d:5:last` | d = 1（Push-T、Two-Room）、2（Cube、Reacher） |
| iCEM-小 + 我们的部件 | iCEM 100×5 | `clamp:1:1:5:min` | |
| MPPI 部署 | MPPI 300×10 | `sync:5:2:10:last` | 官方 MPPI 148–187 ms，2 步 |
| MPPI + 我们的部件 | MPPI 300×10 | `clamp:1:1:10:min` | |

回合：每组 300 个（与 `docs/real_latency_v1.md` 相同的回合）；指标为 50 步内成功率；配对 bootstrap 95% 置信区间（5000 次）。
Reacher 的官方 CEM 与完整方法取自按 6 / 1 步重跑的 `RL6reacher`。

## 局限

- iCEM、MPPI 的超参用的是常见默认值（iCEM 论文的 β、衰减、精英比例；MPPI 温度 0.1），没有逐环境调参；CEM 也没调。
- 「官方方式部署 iCEM」的延迟是估算值（官方库实现在本模型上跑不通）。估算只影响 iCEM 部署这一列；叠加实验用的是实测的缓存版耗时。
- 50 Hz 的结果见 `docs/rate50hz_v1.md`：iCEM 的速度优势仍然没有变成成功率（承诺前缀把低于一个动作块的延迟完全藏住），完整方法仍然最好。

```bash
FLASH_SOLVER=icem FLASH_N=100 python scripts/e9_realtime.py 250 ISpushtbase sync:5:1:5:last:base clamp:1:1:5:min:base
FLASH_SOLVER=mppi             python scripts/e9_realtime.py 250 MPpushtbase sync:5:2:10:last:base clamp:1:1:10:min:base
python scripts/e11_solver_latency.py pusht 20      # 耗时
```

环境变量前缀（数据、权重、回合文件）与 `docs/real_latency_v1.md` 相同；结果在 `results/e9_realtime_{IC,IS,MP}*.json`。
