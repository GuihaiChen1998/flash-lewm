# Issue #7 评审与验证结果 v1（2026-11-14）

对象：issue #7「Flash-LeWM Inspired by Autoregression Version RTC」及其三条评论（承诺前缀、共享前缀计算、异步预规划、预测状态再锚定）。
环境：Linux#1，RTX A6000（与他人共用），Fast-LeWM 官方 Push-T checkpoint，只做了 Push-T。

## 1. 结论

1. **按 issue 原样（官方代价）不成立。** 官方代价只看整段计划结束时离目标多远。改成每 5 或 10 步重规划后，
   每次都重新规划「25 步后到达」，到达时刻不断后移。前缀钳制 32.7% / 43.7%，整段执行的官方方式 86.0%。
   零延迟也一样（26.3%），所以问题出在目标函数，不在调度。
2. **换代价后机制成立。** 把代价改成「所有前缀长度的终点里离目标最近的一个」（下称 min 代价）。Fast-LeWM 的因果前缀编码器
   一次前向就给出全部前缀状态，所以这只是多算几个预测器 token。之后前缀钳制达到 90.7%（延迟 5 步）和 87.0%（延迟 10 步），
   明显好于朴素异步和同频率的同步暂停。
3. **但在 Push-T 上没有胜过最简单的基线。** 同样用 min 代价、「整段 25 步执行完再暂停重规划」是 88.7% / 88.3%，
   与前缀钳制的差在置信区间内，平均到达时间也相近。加扰动后仍然如此。
4. **这轮最稳的收益来自 min 代价本身**，与异步无关：整段执行、零延迟时平均到达时间从 23.6 步降到 16.0 步；
   有扰动时成功率高 6.0–7.3 个百分点（区间不含 0）。
5. **共享前缀计算**：精确；两条路径同样编译后每次评分省 29–46%（N=300 约 29–35%）。未编译时不省（与 issue #6 的测量一致）。

## 2. 协议

离散事件仿真，时间单位是环境步（Push-T 名义 10 Hz，一步 0.1 s）。规划延迟按整数步 `d` 注入：`d=5` 约等于官方求解器
实测的 467 ms，`d=10` 约 1 s。规划期间物理继续推进：同步方法原地保持，异步方法继续执行已承诺的动作。
所有方法首个计划都付同样的启动等待 `d`。一个计划是 5 块 × 5 步；承诺长度 `m` 以块计，`m=1` 对应 `d=5`，`m=2` 对应 `d=10`。
指标：50 步物理时间内的成功率（暂停计入），300 回合（官方 50 + 另抽 250），配对 bootstrap。CEM 均为 300×30，除非注明。

| 方法 | 含义 |
|---|---|
| oracle | 零延迟同步，每 m 块重规划（不可部署，上界） |
| sync | 观测 → 原地等 d 步 → 执行 m 块 → 重复；`m=5` 就是官方的「整段执行」 |
| naive | 朴素异步：边执行边从当前观测规划一条全自由计划，到达后跳过其前 m 块 |
| clamp | issue 的 V1：把队列里的 m 块钳为所有候选的前缀，只搜后缀 |
| reanchor | issue 的 V2：用模型预测执行完队列后的潜状态，从它出发规划全自由计划 |

## 4. 扰动测试

第 12 步把方块随机平移 12 像素并旋转 ±0.15 rad。300 回合。

| 配置 | 50 步成功率 | 平均到达步 |
|---|---:|---:|
| oracle m=5，官方代价 | 72.7% | 25.7 |
| oracle m=5，min 代价 | 80.0% | 16.2 |
| oracle m=1，min 代价 | 79.3% | 19.3 |
| sync m=5，d=5，官方代价 | 67.7% | 29.8 |
| sync m=5，d=5，min 代价 | 73.7% | 21.5 |
| sync m=1，d=5，min 代价 | 58.7% | 37.0 |
| naive m=1，d=5，min 代价 | 44.0% | 26.7 |
| **clamp m=1，d=5，min 代价** | 75.0% | 23.9 |
| sync m=5，d=10，min 代价 | 67.7% | 26.5 |
| naive m=2，d=10，min 代价 | 49.0% | 25.1 |
| **clamp m=2，d=10，min 代价** | 64.7% | 27.7 |

- clamp − sync m=5（min 代价）：+1.3 [−3.0, +5.7]（d=5），−3.0 [−6.7, +0.7]（d=10）。不显著。
- clamp − naive：+31.0 [+25.0, +37.3]（d=5），+15.7 [+10.3, +21.0]（d=10）。
- min 代价 − 官方代价（同为整段执行）：+7.3 [+2.7, +12.0]（零延迟），+6.0 [+1.7, +10.3]（d=5）。
- 零延迟下每 5 步重规划并不比整段执行好（79.3% 对 80.0%）。在这个任务上更高的反馈频率本身没有带来收益，
  这解释了为什么前缀钳制赢不了整段执行。

## 6. 对 issue #7 的具体意见

1. **issue 漏掉了目标函数的时间一致性。** REALFAST 的策略是生成式的，没有「规划地平线终点」的概念；搬到 CEM + 终点代价上，
   承诺短、重规划勤就会不断推迟到达。这是原样方案失败的唯一原因，也是这轮唯一需要的方法改动。
2. **「省 m/H 的 FLOPs」在 Fast-LeWM 上要求两条路径都编译。** 评论里说收益「比 vanilla 情形省得少」是对的；实测编译后省 29–46%，未编译不省。
3. **V2（预测再锚定）没有比 V1 差多少**，延迟 10 步时持平。issue 担心的组合误差在 Push-T 上不明显，但 V2 也没有带来额外好处。
4. **评论 3 的 R2/R10 是对的。** 必须和「同承诺协议的简单基线」比；这次最强的简单基线就是整段执行 + min 代价，前缀钳制没有赢它。
5. **适用边界**：Push-T 名义 10 Hz、任务 16–25 步就完成，规划延迟相对任务时长很小。要让承诺前缀协议显出价值，
   需要重规划频率本身有用的任务（持续扰动、移动目标、长程任务），或更高的控制频率。

## 7. 局限

- 只有 Push-T、一个 checkpoint；延迟是注入的整数步，不是真实并发执行。
- min 代价下的规划实际耗时没有单独测（预测器要算 5 个 token 而不是 1 个）。
- 扰动只测了一种幅度和一个时刻；最初试的 30 像素 / 0.3 rad 太强（零延迟整段执行只有 23%），已弃用。
- H=5 块限制了 m ≤ 2；没有试更长的地平线（超出训练长度）。
- 300 回合，成功率差的 95% 区间半宽约 3–6 个百分点。
- 仿真里渲染帧代替了官方协议首帧用的数据集帧（两者平均像素差约 0.4/255）。

## 8. 下一步建议

1. 把 min 代价单独拿出来验证：在官方协议（1010 回合）和 Cube 上复核「到达更快、抗扰动更好」是否成立，并测它的实际规划耗时。
2. 若继续做承诺前缀：换到重规划频率有用的设定（持续扰动或移动目标），先确认零延迟下勤重规划优于整段执行，再谈异步。
3. 把 min 代价 + FlashCEM + 编译后的后缀评分合在一起，测真实墙钟下的端到端延迟。
